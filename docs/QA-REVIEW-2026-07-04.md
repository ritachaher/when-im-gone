## CRITICAL — fix before any further testing

### C1. "Lock & exit" from the Survivor view does not lock the vault
`src/App.tsx:108`, `src/ui/Survivor.tsx`, `src/storage/vault.ts:192`
The Survivor screen's Lock & exit button calls `onBack`, wired as `onBack={() => setScreen('lock')}` — it never calls `lock()`. The decrypted journal and data key stay in memory. Anyone at the machine can then click "I'm a loved one" on the Lock screen and re-enter the full journal **with no credentials** (`Survivor.tsx` renders `SurvivorHome` whenever `unlocked` is true). The Lock screen also dead-ends: entering the correct password appears to do nothing because the `unlocked` effect (`App.tsx:47-49`) doesn't re-fire.
**Fix:** `onBack={() => { lock(); setScreen('lock'); }}` and add `screen` to the effect's dependency array.

### C2. Service worker hijacks navigation — login and legal pages break for returning visitors
`dist/sw.js`, `vite.config.ts` (vite-plugin-pwa defaults)
The generated SW registers `NavigationRoute(createHandlerBoundToURL("index.html"))` at scope `/`, and the **marketing page** registers it. For anyone who has visited the landing page once: `/app` (login), `/privacy`, `/terms`, `/about`, and `/blog/*` are all answered from cache with the **landing page** — Azure's rewrites never run.
**Fix:** set `workbox.navigateFallback: '/app.html'` with a `navigateFallbackDenylist` for `/`, `/privacy`, `/terms`, `/about`, `/blog/.*` — or stop registering the SW on the landing page entirely. If testers already have the SW installed, ship a cleanup SW update.

### C3. Printing the recovery sheet can print masked dots — permanent data-loss path
`src/ui/Setup.tsx:335-369`, `src/styles.css` `@media print`
The Print button calls `window.print()` on whatever is rendered: `revealed ? recoveryCode : '••••-••••-••••'`. If the user hasn't clicked Reveal, the printed "keep this in a sealed envelope" sheet contains dots. Worse, Setup re-masks on window `blur`, and the print dialog blurs the window in several browsers — so even a revealed code can re-mask before rasterisation. A user who prints, seals, and later forgets their password has lost everything — the exact failure this product exists to prevent.
**Fix:** print-only element that always contains the code; suppress the blur-mask between `beforeprint`/`afterprint`.

## HIGH

### H1. Survivor unlock path bypasses the brute-force throttle entirely
`src/ui/Survivor.tsx` (SurvivorUnlock) vs `src/ui/Lock.tsx`
The exponential backoff lives only in `Lock.tsx`. `SurvivorUnlock` calls the same `unlockWithPassword`/`unlockWithRecovery` with no throttle and no failure recording — unlimited attempts one click away. The counter is also in `localStorage` (clearable in DevTools), so the comment "an attacker can't bypass it with a page reload" overstates it: your real defence is PBKDF2-600k + password strength. Share the throttle across both surfaces (and consider counting failures in IndexedDB alongside the vault).

### H2. Restore-then-push breaks: `importEncryptedBlob` drops `vaultCloudId`
`src/storage/vault.ts` (ExportPayload / importEncryptedBlob), `src/storage/firebase.ts:97-100`, `src/ui/Owner.tsx`
The `.wig` payload doesn't include `vaultCloudId`, and import writes meta without one. The backfill only runs on **recovery-code** unlock. Common flow: restore backup → unlock with password → "Save a copy" throws `Cloud ID missing`, surfaced only as generic "Could not save - please try again". Cloud backup silently stops. Include `vaultCloudId` in the export payload (it's derivable from the recovery code the blob already requires, so no security change) and surface the specific remediation message.

### H3. Rules-of-Hooks violation crashes Owner to a white screen on wipe
`src/ui/Owner.tsx:56` — `if (!journal) return null;` sits above 4+ hooks. When `wipe()` runs `lock()` before `location.reload()`, Owner re-renders with `journal === null`, React throws "Rendered fewer hooks than expected", and there is no error boundary in `main.tsx`. Move the early return below all hooks; add a top-level error boundary; enable `eslint-plugin-react-hooks`.

### H4. All sitemap/canonical blog URLs serve the noindexed app shell
`public/sitemap.xml`, `staticwebapp.config.json`
Blog canonicals are extensionless (`/blog/what-happens-when-you-die-uk`), but there are no `/blog/*` routes, so they fall through `navigationFallback` to `app.html`, which is `noindex, nofollow`. Every blog URL submitted to Google serves an empty, deindexed shell. Add per-slug rewrite routes (and a `/blog/` index or exclude).

### H5. Privacy notice omits two real processors — GDPR exposure
`public/privacy.html` vs actual data flows:
- **HIBP:** setup sends the first 5 hex chars of SHA-1(password) + user IP to `api.pwnedpasswords.com` (`src/crypto/password-strength.ts`). Not mentioned anywhere in "What we do see". Data derived from the master password going to a third party must be disclosed (the k-anonymity design is defensible — say so).
- **Resend:** every opt-in email is relayed through Resend's SMTP (US processor) by `notifyOnSubscriber` (`functions/src/index.ts`), but the policy says the email is only stored in Firestore and "never shared". The International Transfers section mentions only Firestore.

### H6. Vulnerable dependencies
`npm audit`: 5 vulnerabilities (2 high — vite `server.fs.deny` bypass, react-router; 2 moderate; 1 low). All have fixes via `npm audit fix`. Run it and re-test before launch.

## MEDIUM

**M1. App Check still disabled in rules.** `firestore.rules` `appCheck()` returns `true`. Your own May-2026 audit handoff (docs/SECURITY-H1-H5-HANDOFF.md) designates enabling App Check as the accepted H1 remediation, and it's the main mitigation against scripted access: today any anonymous-auth client can (a) create unlimited `vaults` docs up to 1 MB each (cost/spam — no per-UID quota) and (b) probe/overwrite a vault doc if it ever learns the ID. Follow the handoff's 5 steps before launch. Also split `allow read` into `allow get` + `allow list: if false` to make non-enumerability explicit.

**M2. `pairViaRecoveryCode` hard-codes `{ confirmedReplace: true }`** (`src/storage/firebase.ts:151`), silently defeating the destructive-import guard for any future caller. Make it a pass-through parameter.

**M3. Concurrent `save()` calls can silently lose data** (`src/storage/vault.ts:196-205`). Every keystroke triggers snapshot → encrypt → write with no serialisation; overlapping saves start from the same snapshot and the later commit clobbers the earlier field. Silent data loss is the worst failure class for this product. Serialise saves through a promise queue.

**M4. `importEncryptedBlob` doesn't validate the payload** beyond `format === 'wig/1'`. A truncated/corrupt file (missing base64 fields → `atob(undefined)` throws mid-write, or writes garbage meta) can brick the local vault after the destructive replace has begun. Validate all fields *before* touching IndexedDB, and write meta+journal in one Dexie transaction.

**M5. `DateInput` accepts impossible dates** (`src/ui/fields.tsx` — `45/13/2020` stores `2020-13-45`); downstream `isUnder18` gets `Invalid Date` → returns false → guardian fields silently hidden for a mistyped child DOB. Partial clears also silently retain the old committed date. Add range validation + commit-on-blur.

**M6. Ghost Firebase Hosting origin.** `firebase.json` no longer has a hosting section, but `.firebase/hosting.ZGlzdA.cache` shows a May deploy. If `when-im-gone-314f6.web.app` is still live it serves a stale build on a second origin with **no CSP/HSTS/XFO headers**. Disable the Hosting site or configure it with equivalent headers.

**M7. SW precaches marketing + legal pages** — pricing/beta banner and "Last updated" legal text can be served stale after a deploy. Exclude them via `globIgnores`.

**M8. Privacy "not linked in any way" overclaims.** The subscriber write runs after `ensureAnonUser()` — same anonymous UID (and IP) as vault pushes; Google-side logs can correlate. Soften to "we do not store any link" (also fix the same claim in `src/storage/firebase.ts` docstring).

**M9. Survivor unlock screen is hard-coded English** — the one screen guaranteed to be seen by a grieving relative who didn't choose the app. Every string in `SurvivorUnlock` bypasses i18n. Also: i18n key collision — Owner reuses `lock_hint`, so the sidebar shows "Unlock your journal to continue." under the Lock button.

**M10. Inline `onerror` handler violates your own CSP** (`index.html:1871`) — `script-src 'self'` blocks it, so the book-cover fallback never runs and every load logs a CSP violation. Move to external JS.

**M11. Terms don't match reality (beta).** Terms promise email notice of changes (most users have no email on file), describe a £12.95 checkout + 14-day-waiver checkbox that doesn't exist, and cap liability at "the £12.95 you paid" (£0 for beta users). Align before launch. Also `privacy.html` documents localStorage key `wig-lang` but the marketing site uses `wig_lang` (and the language choice doesn't carry into the app).

- **L7.** A11y: sidebar nav uses `<a>` without `href` (not keyboard/screen-reader accessible); dialogs lack focus trap and Escape handling.

- **L10.** CI: pin GitHub Actions to commit SHAs (workflow holds the deploy token). Note same-repo PR previews are internet-reachable with the prod Firebase config (config is public-by-design; just be aware).
